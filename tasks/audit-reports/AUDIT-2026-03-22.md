## Architecture Notes

### Dual DnD Library in contacts/page.tsx
`contacts/page.tsx` imports BOTH `@hello-pangea/dnd` AND `@dnd-kit/core` + `@dnd-kit/sortable`. This is intentional (kanban row drag = hello-pangea, column header reorder = dnd-kit) but doubles DnD bundle weight and adds complexity. The two libraries solve different UIs — acceptable for now, but worth documenting so future devs don't add a third.

### arive-webhook raw-fetch pattern
`src/app/api/arive-webhook/route.ts` imports `createServiceClient` but then implements its own raw `fetch` helpers (`sbUpsert`, `sbInsert`, `sbHeaders`). The SDK client is used only for org resolution (line 148). The raw helpers predate the SDK client import and were never migrated. Risk: low (they work), but if the Supabase URL or key structure changes, two code paths need updating.

### refi-intake bypasses shared Anthropic client
`src/app/api/automations/refi-intake/route.ts` calls the Anthropic API via raw `fetch` using `process.env.ANTHROPIC_API_KEY` directly — it does NOT use `getAnthropicClient()` from `lib/anthropic/client.ts`. This means:
- If Adam saves his API key in Settings → Integrations, the refi-intake automation won't pick it up
- If the model changes, this file won't update automatically

### No shared CLAUDE_MODEL constant
All 8 Claude API calls across the codebase hardcode `model: 'claude-sonnet-4-5'`:
- `api/chat/route.ts`
- `api/agents/daily-briefing/route.ts`
- `api/agents/milestone/route.ts` (×2)
- `api/scenarios/generate-narrative/route.ts`
- `api/scenarios/parse-statement/route.ts`
- `api/automations/refi-intake/route.ts`
- `api/outreach/route.ts`

If the model string needs to change, 8 files must be edited manually.

### Performance page uses localStorage with hardcoded seed data
`src/app/dashboard/performance/page.tsx` is entirely client-side with:
- `STORAGE_KEY = 'loanDashboard2026'` (persisted to localStorage)
- `SEED_LOANS` array with real borrower last names (Voelkel, Aguilar, Stackhouse, etc.)
- No Supabase connection

This page is a standalone tracker that doesn't read from the loans table. Data will diverge from Supabase. Privacy concern: real borrower names in source code.

### orphan tables: kids, challenges, responses
Three tables in the public schema — `kids` (3 rows), `challenges` (90 rows), `responses` (0 rows) — have no references anywhere in `src/`. These appear to be a personal project (kids/Bible challenges?) that accidentally shares the Supabase instance. They have RLS enabled. Not a security risk, but they pollute the schema and any future `generate_types` output.

### build-tracker is an iframe
`src/app/dashboard/build-tracker/page.tsx` renders an iframe pointing to `/docs/loanos.html`. The HTML file is static. This page requires auth but provides no value over a bookmark. Low priority.

## Supabase Schema Audit

### Missing indexes (high priority for performance)
These tables have no index on their most-queried FK columns. At current data volume (contacts: 2,371 rows, loans: 851 rows, activity_log: 267 rows) this is fine. At 10,000+ rows queries will slow noticeably.

| Table | Missing Index On |
|-------|-----------------|
| `contacts` | `organization_id` |
| `loans` | `organization_id`, `contact_id` |
| `activity_log` | `organization_id`, `loan_id`, `contact_id` |
| `contact_activity` | `contact_id`, `loan_id` |
| `loan_status_history` | `loan_id` |
| `documents` | `loan_id`, `organization_id` |

### Missing FK constraints (low priority — RLS covers correctness)
Most `_id` columns have no formal FK constraint (e.g., `loans.contact_id` → `contacts.id`). Supabase won't enforce referential integrity at the DB level. Orphaned records can accumulate if a contact is deleted. RLS prevents data leaks but not orphans.

### oauth_state table — 55 stale rows
`oauth_state` has 55 rows with no cleanup job. These are short-lived OAuth state tokens that should expire. A cron job or periodic cleanup would keep this clean.

### kids / challenges / responses — foreign tables
3 rows, 90 rows, 0 rows respectively. No FK to any LoanOS tables. Should confirm with Adam whether these belong here or in a separate project's DB.

### RLS — all tables correct
Every table in the schema has RLS enabled. No open tables found.
