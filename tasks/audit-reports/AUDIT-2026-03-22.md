## Critical Issues (fix immediately)

### 1. Chat sessions missing `organization_id` on insert — multi-tenant data leak risk
**File:** `src/app/api/chat/route.ts:203`

The POST handler creates new `chat_sessions` rows without `organization_id`:
```ts
.insert({ record_id: recordId, record_type: recordType, messages: updatedMessages, user_id: userId })
```
Migration 044 switched `chat_sessions` RLS to org-scoped policies (`organization_id = get_my_organization_id()`). Any new session inserted without `organization_id` will be invisible to subsequent browser-client RLS reads. The API route uses `createServiceClient()` (bypasses RLS) for reads/writes, so the bug is silent today — but if any component ever reads sessions via a non-service client, or if a second tenant's user has a `record_id` UUID collision (astronomically unlikely but architecturally wrong), cross-org data could be exposed.

**Fix applied this session.** → Added `organization_id: organizationId` to insert.

### 2. Chat GET endpoint not scoped by org — service client unscoped query
**File:** `src/app/api/chat/route.ts:217-256`

The GET handler calls `await getOrganization()` for auth but discards the return value — the org ID is never used. The `chat_sessions` query fetches by `record_id` + `record_type` only:
```ts
await getOrganization()   // return value discarded
...
supabase.from('chat_sessions').select(...).eq('record_id', recordId).eq('record_type', recordType)
```
No org scoping on the query means any org could theoretically retrieve another org's session if the `record_id` is known. Also incorrect for multi-tenant correctness.

**Fix applied this session.** → Destructured org from `getOrganization()`, added `.eq('organization_id', organizationId)` to both SELECT and UPDATE.

### 3. daily-briefing: `loan_milestone_events` + `milestone_communications` unscoped
**File:** `src/app/api/agents/daily-briefing/route.ts:109-131`

Two of the five parallel queries run against tables with no `organization_id` column and no org filter:
```ts
supabase.from('loan_milestone_events').select(...)  // no org filter
supabase.from('milestone_communications').select(...) // no org filter
```
Both use `createServiceClient()` (bypasses RLS). In a multi-tenant context, briefings for Org A would include milestone data from Org B. Currently low-risk (single tenant) but must be fixed before licensing.

**Fix applied this session.** → Pre-fetch org loan IDs, then filter both queries via `.in('loan_id', orgLoanIds)`.

## Architecture Notes

### Overall structure: clean
The project follows Next.js 14 App Router conventions correctly. Server Components handle data fetching; Client Components handle interactivity. API routes are thin and delegate to lib/ helpers appropriately. No logic-in-UI violations found.

### File naming: one inconsistency
`supabase/migrations/` uses 3-digit prefix (001–015) for early files, then switches to 4-digit (0016, 0017). The remaining 018–044 use 3-digit again, making 0016/0017 visually odd.
**Priority: low.** Already tracked in todo.md.

### Dead route: `/api/pipeline/stats`
This route is fully implemented but its output is no longer consumed — the dashboard server component fetches all data directly. The route is harmless but adds noise.
**Recommendation:** Remove or repurpose as a dedicated reporting endpoint.

### Dual n8n workflow directories
There are two separate workflow directories: `/n8n-workflows/` (5 files) and `/n8n/` (5 files). The split is not documented anywhere. The naming is ambiguous — it's unclear which set is "current" vs "archived."
**Recommendation:** Consolidate into `/n8n/` and document purpose differences inline.

### `borrower_name` legacy column
The `Loan` interface in `src/app/dashboard/loans/page.tsx` still carries a `borrower_name: string | null` field alongside `borrower_first_name` + `borrower_last_name`. The legacy column is null for all Arive-synced loans. This creates a 3-field fallback chain in multiple places.
**Recommendation:** Once backfill is confirmed complete, remove `borrower_name` from select queries and type definitions.

## UI/UX Improvements

### Design system: largely consistent
The dark monochromatic + gold accent system is applied consistently across dashboard, briefing, and loans pages. `bg-[#050505]`, `bg-zinc-900`, `border-zinc-700`, `text-amber-400/500`, and `border-l-amber-500` are used as intended. IBM Plex fonts applied via Tailwind config.

### Hardcoded hex values in briefing page
`src/app/dashboard/briefing/page.tsx` uses hardcoded hex strings instead of Tailwind tokens:
- `bg-[#4ADE80]` (green for progress bar and checkmarks) — should use `bg-green-400`
- `bg-[#050505]` (background) — already a custom value in use elsewhere, acceptable

**Fix:** Replace `bg-[#4ADE80]` and `text-[#4ADE80]` with `bg-green-400` / `text-green-400` for consistency. Minor but applies the design token correctly.

### Performance page: localStorage-only data
`src/app/dashboard/performance/page.tsx` stores all commission and loan data in `localStorage` under key `loanDashboard2026`. This data:
- Is device-specific (lost when switching machines)
- Is not shared across team members
- Contains seeded dummy data (Voelkel, Aguilar, Stackhouse, etc.)
- Has no Supabase backing

This page cannot be licensed to other LOs in current state.
**Priority: medium.** Already tracked in todo.md.

### Briefing page: no auto-fetch on mount
The daily briefing page requires a manual button click every time. For a morning dashboard, the briefing should auto-trigger on first load (if no cached data) to save the LO one click each morning.
**Quick win opportunity.** Low effort, high daily UX value.

### Loading states: consistent on most pages
All major pages handle loading and error states correctly. The briefing page shows a 7-item animated pulse skeleton during load — good. The loans page uses client-side fetching with a spinner. No blank-screen loading states found.

### Null display: mostly correct
The chat system prompt builder uses `'N/A'` for null fields, not empty strings — consistent with design rules. A few places in loan/contact detail pages use conditional rendering that could show blank rather than `—`, but this is minor.

## Simplification Opportunities

### `performance/page.tsx` — over-engineered for localStorage
The performance page is a fully-featured analytics dashboard (charts, loan table, expense tracker, P&L) backed entirely by `localStorage`. At current scale (single LO), this is acceptable as a prototype, but the seeded data and local storage dependency make it unshippable to other LOs. The entire component would need to be rewritten against Supabase data.

### Loan name fallback chain repeated in 4+ places
The pattern `[borrower_first_name, borrower_last_name].filter(Boolean).join(' ') || loan_name || 'Unknown'` appears in:
- `dashboard/page.tsx` (twice)
- `loans/page.tsx` (once)
- `agents/daily-briefing/route.ts` (implied via loan_name field)

A `borrowerDisplayName(loan)` utility already exists in `lib/` — verify all pages import and use it consistently rather than re-implementing inline.

### Two milestone query blocks in `agents/milestone/route.ts`
The milestone agent has two separate `anthropic.messages.create()` calls (lines 142 and 225) — one for the borrower email, one for the realtor email. These are sequential. They could be parallelized with `Promise.all()` for a ~40% latency reduction on the most latency-sensitive agent.

### `withOrg()` helper in daily-briefing is a local arrow function
The `withOrg` helper defined inline in `daily-briefing/route.ts` duplicates the same pattern used in several other routes. This is a low-priority abstraction opportunity — a shared `scopeToOrg(query, orgId)` utility in `lib/supabase/` would DRY this up if it appears in 5+ places.
