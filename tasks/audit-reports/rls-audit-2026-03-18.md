## Issues Found & Fixed

### contact_emails — USING(true) / WITH CHECK(true)

**Problem:** Single policy `"service role full access"` with `USING (true)` and `WITH CHECK (true)` on ALL operations. Any authenticated user could read, insert, update, or delete any row across any organization.

**Root cause:** The original migration comment said "service role only (same pattern as email_drafts)" but that intent was not enforced — the service role bypasses RLS automatically, so a `USING (true)` policy actually opens the table to *all* authenticated users, not just the service role.

**Table structure:** No `user_id` or `org_id` column. Has `loan_id` (FK → loans) and `contact_id` (FK → contacts), both of which carry `organization_id`.

**Fix:** Migration `037_fix_contact_emails_rls.sql`
- Dropped: `"service role full access"`
- Created: `contact_emails_select` — scoped via `loan_id IN (loans by org)` OR `contact_id IN (contacts by org)`
- Created: `contact_emails_insert` — same org scope via WITH CHECK
- Created: `contact_emails_update` — same org scope on USING + WITH CHECK
- Created: `contact_emails_delete` — restricted to org owners/admins only

**Note on service role:** The service role (used by n8n automation workflows that call `logEmail()`) bypasses RLS entirely in Supabase. No explicit service-role policy is required — the new scoped policies only affect authenticated user-context requests.

## Final State

Re-audit query after migration:

```sql
SELECT tablename, policyname, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public'
  AND (qual = 'true' OR with_check = 'true');
```

**Result: 0 rows.** No `USING(true)` or `WITH CHECK(true)` policies remain in the public schema.
