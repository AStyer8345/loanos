## Critical Issues (fix immediately)

### 1. `/api/pipeline/stats` uses dead column names
`/src/app/api/pipeline/stats/route.ts` selects `est_closing_date` and `borrower_name` — both columns no longer exist in the Arive-expanded schema. The real columns are `estimated_closing_date`, `borrower_first_name`, and `borrower_last_name`. Route is currently unwired from the UI, so it silently returns bad data. Will break any future consumer.

### 2. `chat_sessions` RLS is dangerously open
`USING (true)` on chat_sessions SELECT lets any authenticated user read every chat session in the database. Multi-tenancy migrations (029–031) fixed RLS on loans/contacts but did not touch chat_sessions. Before licensing to even one other LO, any user could read any other user's AI conversations.

### 3. `/api/agents/*` middleware exclusion exposes authenticated endpoints
The `middleware.ts` matcher excludes `api/agents/*` from session auth — originally intended for webhook endpoints. But `/api/agents/daily-briefing` and `/api/agents/milestone` are also under `api/agents/`. The briefing route accepts either a session cookie or agent secret, so the exclusion is harmless today, but the matcher is logically wrong and sets a bad precedent. A future `api/agents/something-destructive` route would be publicly accessible.

### 4. Performance page data lives in localStorage only
`/dashboard/performance` stores all P&L data in `localStorage` key `loanDashboard2026` and seeds from hardcoded `SEED_LOANS` constants containing real loan names and amounts (Voelkel, Aguilar, Stackhouse, etc.). This is: (a) device-specific — lost on browser clear, (b) hardcoded production data in source code, (c) completely incompatible with multi-tenancy. This page will not function correctly if LoanOS is licensed to other LOs.

### 5. `stageNormalization.ts` partially duplicates `loan-stages.ts` constants
Two separate normalization systems exist side by side. `stageNormalization.ts` maps Arive/raw statuses to contact stage strings ('Lead', 'In Process', etc.). `loan-stages.ts` maps the same raw values to `StageKey` enum values. They have different output vocabularies. The contacts page imports `normalizeStage` from the old file; the loans pipeline imports `normalizeToStageKey` from the new constants. This will diverge over time.

## Architecture Notes

**Good structure overall.** The App Router layout is clean. API routes are logically organized under `/api/`. The `lib/` folder has proper separation: supabase clients, auth helpers, scoring, scenarios. The `constants/loan-stages.ts` file is excellent — single source of truth with good JSDoc.

**Issues:**

- `netlify/functions/` directory still exists at project root with 5 JS files (`arive-webhook.js`, `outlook-auth.js`, `outlook-callback.js`, `outlook-refresh.js`, `outlook-sync.js`). These are the pre-Vercel versions of routes that now live in `src/app/api/`. They are dead code, but their presence is misleading and adds maintenance confusion.

- `src/lib/stageNormalization.ts` is a legacy file from before `loan-stages.ts` was built. It has a smaller mapping table and returns different output strings. Still imported in 4 places. Should be unified into `loan-stages.ts` or eliminated.

- `src/app/api/contacts/[id]/` has no `route.ts` — only a subdirectory for `activity`. The contacts detail page (`contacts/[id]/ContactRecordView.tsx`) appears to make direct Supabase client calls rather than going through a REST API layer. Inconsistent with the loans pattern.

- The `arive-webhook` route does its own raw fetch to Supabase instead of using the existing `createServiceClient()` helper. It re-implements `sbHeaders()`, `sbUpsert()`, and `sbInsert()` as local functions. This means any Supabase URL change has to be made in two places.

- Two drag-and-drop libraries are installed: `@hello-pangea/dnd` (used for contacts row reorder) and `@dnd-kit/core` + `@dnd-kit/sortable` (used for contacts column reorder). Both are active dependencies. This is redundant — the entire contacts DnD could use one library.

## UI/UX Improvements

**Design system is mostly consistent across core pages.** The dark monochromatic + gold system is applied correctly to: Dashboard, Loans, Contacts, Briefing, Emails, Automations, Reports.

**Inconsistencies found:**

1. **Login page** (`/src/app/page.tsx`) uses `bg-gray-950` / `bg-gray-900` / `bg-blue-600` — completely off-system. No IBM Plex fonts. No gold accent. No `--bg` / `--surface` tokens. It's the first thing anyone sees and it looks like a generic SaaS starter template.

2. **Scenario Builder** (all files under `scenarios/new/`) uses a completely different design system: `--sc-bg` (#0c1220 navy), `--sc-blue` (#5b8def), `--sc-card` (#111a2e). Font is hardcoded `'Inter', sans-serif` in 18+ inline style declarations. This section is intentionally separated (documented in CONTEXT.md), but the Inter font references are incorrect — `globals.css` loads IBM Plex Mono/Sans via Google Fonts, not Inter. Inter is not in the font stack. These calls will silently fall back to the OS sans-serif font.

3. **NavBar** uses `bg-[#060b18]` / `border-[#1e293b]` (navy-tinted), while the dashboard layout uses `bg-zinc-950`. The layout wrapper and the nav have different base colors. Subtle but visible on pages with wide viewports.

4. **Mobile nav** uses `bg-slate-950/95` — a third distinct background value. The app currently has three different dark backgrounds: `#050505` (CSS var `--bg`), `#060b18` (nav/dashboard), `bg-zinc-950` (layout wrapper). They should all be `var(--bg)`.

5. **Reports pages** (commission, volume) use hardcoded `bg-[#060b18]` / `bg-[#0f172a]` / `border-[#1e293b]` — navy palette inconsistent with the rest. These pages should use `--bg`, `--surface`, `--border`.

6. **fmtCurrency / fmtDate / fmtK** are redefined in 10+ separate files. These should live in `src/lib/formatters.ts` and be imported everywhere.

**Loading states:** Loans and Contacts pages handle loading correctly with skeleton rows. Briefing page has a good loading skeleton. Reports/Performance pages show a blank `min-h-screen` div while loading — no skeleton.

**Error states:** Most pages catch errors and show inline error messages. The Scenario Builder's `error.tsx` exists. The Briefing page shows an error message. Good coverage.

## Simplification Opportunities

1. **Create `src/lib/formatters.ts`** — `fmtCurrency`, `fmtDate`, `fmtK`, `fmtPct` are each defined 5–10 times across the codebase. A single shared module eliminates ~60 lines of duplicate code and ensures consistent formatting behavior everywhere.

2. **Consolidate `stageNormalization.ts` into `loan-stages.ts`** — contacts need a `contactStageFromLoanKey()` bridge (which already exists in `loan-stages.ts`) and a simpler pass-through for UI display labels. The legacy `normalizeStage()` in `stageNormalization.ts` can be replaced by mapping `normalizeToStageKey()` output through `contactStageFromLoanKey()`.

3. **Fix `arive-webhook/route.ts` to use `createServiceClient()`** — the route has its own 50-line reimplementation of Supabase helpers. Replace with the existing `createServiceClient()` from `src/lib/supabase/service.ts`.

4. **Delete `netlify/` directory** — 5 functions that are dead code. All functionality now lives in `src/app/api/`.

5. **Pick one DnD library** — `@hello-pangea/dnd` and `@dnd-kit/core` both install ~140KB of JS. The contacts page uses both simultaneously. Standardize on `@dnd-kit` (already used for column reorder) and migrate the row reorder drag behavior.

6. **Move Performance page data to Supabase** — hardcoded seed loans with real borrower names in source code is a problem. This blocks licensing.

7. **Scenario Builder Inter → IBM Plex Mono** — 18 inline `fontFamily: "'Inter', sans-serif"` declarations. Inter is not loaded; these silently fall back to OS default. Replace with `'IBM Plex Mono', monospace` or `'IBM Plex Sans', sans-serif` to match the design system.
